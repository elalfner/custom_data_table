## Context

`CustomDataTable` is a customizable Flutter data table widget providing horizontal/vertical scrolling, column sorting, search filters, and server-side pagination controls via `PaginatorInfo`.

In `lib/src/presentation/widgets/custom_data_table.dart`, state evaluation conflated data availability with pagination metadata:
```dart
final error = (data == null || paginator == null) && !widget.isLoading;
...
if (data == null || paginator == null) {
  if (widget.isLoading) {
    return widget.loadingBuilder?.call() ?? const CircularProgressIndicator();
  } else {
    return widget.exceptionBuilder?.call() ?? const SizedBox();
  }
}
```

When callers provided non-null `data` with `paginatorInfo: null` (for static lists, local collections, or unpaginated endpoints), the table incorrectly fell into the error/loading branch, rendering a blank `SizedBox()`.

## Goals / Non-Goals

**Goals:**
- Decouple data presence validation from `paginatorInfo` presence.
- Support unpaginated tables: when `data != null` and `paginatorInfo == null`, render all rows, headers, and column filters normally while omitting pagination controls in the footer.
- Provide a convenience constructor `PaginatorInfo.singlePage({required int total})` for explicit single-page configurations.
- Provide documentation and idiomatic extension snippets for GraphQL Lighthouse and `graphql_codegen` consumers.
- Preserve 100% backward compatibility with existing applications (such as `viali_panel`).
- Ensure complete automated test coverage (widget tests and unit tests).

**Non-Goals:**
- Implement in-memory client-side pagination partitioning within `CustomDataTable`.
- Modify backend APIs or schema contracts.
- Alter the public signature of `CustomDataTable` other than updating docstrings and allowing null paginator safely.

## Decisions

### 1. State Evaluation Decoupling in `CustomDataTable`
- **Choice**: Change the error predicate to `final error = data == null && !widget.isLoading;` and the builder branch condition to `if (data == null)`.
- **Alternatives Considered**:
  - *Keep `paginatorInfo` mandatory and force callers to use `PaginatorInfo.singlePage`*: Rejected because requiring dummy metadata for unpaginated tables adds unnecessary boilerplate and breaks developer expectations.
  - *Add a separate `isPaginated` boolean flag*: Rejected because `paginatorInfo == null` already cleanly communicates the absence of pagination metadata.
- **Footer Handling**: `footer()` in `CustomDataTable` already returns `const SizedBox()` when `paginatorInfo == null`. With the body check decoupled, the table body renders completely and the footer safely takes zero space without visual jumps or constraint warnings.

### 2. Convenience Factory `PaginatorInfo.singlePage`
- **Choice**: Implement `factory PaginatorInfo.singlePage({required int total})` setting:
  - `currentPage: 1`
  - `lastPage: 1`
  - `perPage: total`
  - `total: total`
  - `count: total`
  - `hasMorePages: false`
- **Rationale**: Meets GraphQL Lighthouse schema conventions for unpaginated or single-page payloads where callers still need a concrete `PaginatorInfo` object.

### 3. Documentation of GraphQL Lighthouse Integration
- **Choice**: Document in `README.md` the 1:1 mapping between Lighthouse's GraphQL `PaginatorInfo` fragment and `custom_data_table`'s `PaginatorInfo` entity, demonstrating an extension method on `Fragment$Paginator` generated by `graphql_codegen`.
- **Rationale**: Establishes standard integration guidance without adding direct package dependencies on GraphQL libraries.

## Risks / Trade-offs

- **[Risk] Existing callers relying on `paginatorInfo: null` to blank out the table**
  - *Mitigation*: Passing valid `data` while expecting a blank table is an anti-pattern. If a caller wants an empty state, they should pass `data: []` or `data: null`.
- **[Risk] Layout regression when `TableFooter` is omitted**
  - *Mitigation*: `footer()` already returns `const SizedBox()`. Automated widget tests will assert proper layout rendering without viewport or flex overflow errors.
